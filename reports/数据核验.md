# B、C 实验数据独立核验

核验对象为本项目保存的 PostgreSQL 17.6 实测结果。本次核验只读取文件，不连接数据库，不重跑查询，不修改采集或分析脚本。核验脚本为 `scripts/verify_results.py`，仅依赖 Python 标准库。

## 1. 实际完成数量

| 项目 | 数量与范围 |
|---|---|
| 不同 SQL | 20 条，其中 12 条 TPC-H 教学查询、8 条合成数据查询 |
| query-phase 组合 | 36 个：baseline 20 个，reanalyze_control 8 个，extended 8 个 |
| 每个组合执行次数 | 1 次预热 + 3 次正式测量 |
| 原始 JSON 计划 | 144 份 = 36 份预热 + 108 份正式测量 |
| baseline 计划 | 80 份 = 20 份预热 + 60 份正式测量 |
| reanalyze_control 计划 | 32 份 = 8 份预热 + 24 份正式测量 |
| extended 计划 | 32 份 = 8 份预热 + 24 份正式测量 |
| 全部节点记录 | 364 条，包含预热节点 |
| Actual Loops > 1 的节点记录 | 20 条，均按每次执行行数计算 Q-error |

144 次执行不等于 144 条不同查询。108 次正式测量也不构成 108 个独立 SQL 样本；计时重复用于描述同一查询的波动。

## 2. 逐文件一致性核验

2026 年 10 月 2 日执行 `python scripts/verify_results.py`，全部检查通过：

1. 20 条 SQL 的 ID、中文标题、分组、来源及 SQL SHA-256 与 `query_runs.csv` 一致；每个 `(phase, query_id, repeat)` 键完整且唯一。
2. 144 个 `plan_file` 均指向项目 `results/plans` 下真实存在的 JSON，文件总数一致。
3. CSV 中的根节点 Estimated Rows、Actual Rows、Actual Loops、Cost、节点时间、Execution Time、Planning Time 均与原始 JSON 一致。
4. 所有根节点 Actual Loops = 1，没有 Aggregate、Limit、Gather 或 Gather Merge 根节点，实际测量的是完整 SPJ 输出基数。
5. 每份 JSON 都记录 `max_parallel_workers_per_gather=0`、`work_mem=64MB`、`jit=off`，测量连接设置一致。
6. 全部节点的路径、父路径、节点类型、表名、别名、行数、loops、时间、Cost 与 JSON 对应。当前所有节点都具有 Actual Rows 字段，没有把缺失字段冒充零行。
7. 严格 Q-error 和零值平滑 Q-error 逐行重算一致。多 loops 节点用 Plan Rows / Actual Rows 的单次口径；累计处理量另记为 Actual Rows × Actual Loops。
8. 同一 SQL 在各次执行与统计变体下的 Actual Rows 完全相同。
9. TPC-H SF=1 八表行数与数据生成结果一致，其中 orders 为 1,500,000 行、lineitem 为 6,001,215 行；三张同表合成数据各 300,000 行，跨表客户/订单分别 10,000 / 300,000 行。

三个单列统计快照 `stats_baseline.json`、`stats_reanalyze_control.json`、`stats_extended.json` 的 SHA-256 完全相同：

```text
3020c3b3c3ef6f2ddbb9d982cb7ff5930f4164790cf1dae3a7003ca31c7cb6e5
```

因此，本次对照中保存的单列统计没有发生变化；单独重新 ANALYZE 也未改变合成查询的基数估计。这为将 S16/S18/S19 的估计变化归因于新增同表扩展统计提供了有力控制证据。

## 3. 核心数值复核

下面的 estimated/actual 来自原始计划，非手工预测；相同 query-phase 的重复执行具有相同基数。

| 查询 | baseline estimated | actual | baseline Q-error | extended estimated | extended Q-error |
|---|---:|---:|---:|---:|---:|
| S13 独立表单列 | 3,000 | 3,000 | 1 | 3,000 | 1 |
| S14 相关表单列 | 3,000 | 3,000 | 1 | 3,000 | 1 |
| S15 独立表双列 | 30 | 30 | 1 | 30 | 1 |
| S16 相关表相容双列 | 30 | 3,000 | 100 | 3,000 | 1 |
| S17 不相容组合 | 30 | 0 | 严格定义不适用 | 1 | 严格定义不适用 |
| S18 倾斜热门组合 | 75,000 | 150,000 | 2 | 150,000 | 1 |
| S19 倾斜稀有组合 | 8 | 1,515 | 189.375 | 1,515 | 1 |
| S20 跨表相关连接 | 30 | 3,000 | 100 | 30 | 100 |

S17 在正数比值定义下分母为 0，不与正基数 Q-error 混算。当前 CSV 的严格 Q-error 留空，`q_error_safe` 使用 `max(estimated,1)`、`max(actual,1)`，从 30 变成 1。这个平滑值 1 不表示优化器预测到了零行；实际估计仍是 1 行。

TPC-H 的 T09 三表日期条件查询 estimated=316,503，actual=30,519，Q-error=10.370687。其底层 lineitem 过滤为 3,247,322 / 3,241,776，orders 过滤为 728,685 / 727,305，customer 过滤为 30,095 / 30,142；这些单表估计均接近真实值。customer-orders 中间连接为 146,199 / 147,126，而最终与 lineitem 连接时误差显著增大。这与订单日期和发货日期在连接后的相关关系相符；不能概括为“表越多必然越不准”。

S20 两侧单表过滤都完全准确：订单邮编 estimated=actual=3,000，客户城市 estimated=actual=100，但最终 Join 估计 30、实际 3,000。这个案例直接展示了单表估计准确仍可能发生跨表关联误差；本轮同表扩展统计未修复它。

## 4. 执行计划与时延结论的边界

核验脚本比较了节点类型、连接类型、表、别名、索引以及子树结构。S13–S20 在全部三个 phase 和重复运行中的物理计划形状均相同。S16/S18/S19 的基数准确度提高，未观察到算法或连接顺序切换。

| 查询 | reanalyze_control 正式测量中位数 ms | extended 正式测量中位数 ms |
|---|---:|---:|
| S16 强相关双列 | 9.813 | 9.792 |
| S18 倾斜热门 | 16.323 | 17.716 |
| S19 倾斜稀有 | 9.399 | 9.559 |
| S20 跨表相关 | 11.666 | 11.456 |

上述数字仅描述带 EXPLAIN ANALYZE 仪表开销的服务端 Execution Time。每组只有 3 次正式测量，且阶段按 baseline → reanalyze_control → extended 顺序采集；不能把这些小幅波动宣称为显著加速或端到端性能收益。一次预热也不意味着所有数据始终驻留 PostgreSQL shared buffers；部分正式计划仍记录了 Shared Read Blocks。

Total Cost 是优化器抽象成本单位，不能与毫秒求“代价 Q-error”。本次部分估计明显改善但全表扫描的 Cost 与物理计划仍不变，这是有效观察，不应改写为已经证明的“基数误差 → 错误计划 → 性能劣化”完整因果链。

本实验没有训练、推理或接入 MSCN、DeepDB、NeuroCard 等模型。它支持的是关于相关性建模和统计边界的实证结论，以及学习型估计的研究动机；AI 方法性能仍需引用文献或另做模型实验。

## 5. 复查命令

在项目的实验工作区运行：

```powershell
python scripts/verify_results.py
```

或显式指定实验工作区：

```powershell
python scripts/verify_results.py --root 'D:/数据库小组作业/实验工作区'
```

脚本只读静态文件，失败时抛出异常并返回非零退出码。它可验证本次保存产物的一致性，不能代替从数据生成、数据库导入到查询执行的完整独立复现。
