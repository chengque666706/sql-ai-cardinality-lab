**前沿趋势总结**

引言

在前期分析中，我们已经基于 B/C/D 的 PostgreSQL
基数估计实验，明确了传统统计的能力边界，并把 S16/S19、S20、T09、T11
等实验问题映射到 MSCN、DeepDB、NeuroCard、PRICE
等学习型方法。然而，回答"哪类 AI
方法对应哪类实验问题"只是第一步。要判断这些方法能否真正进入数据库优化器，还需要进一步审视它们在工程落地与未来演进中的方向。为此，本部分从多个角度梳理学习型基数估计的前沿趋势，包括：从单库准确率走向跨库可迁移、从模型准确率走向系统级收益、从全替代走向协同共生、冷启动与在线学习、可解释性与轻量化推理、与硬件新特性协同，以及端到端学习优化、工作负载级优化、知识与数据混合驱动、云原生与分布式、大语言模型辅助等延伸方向。每条趋势按"趋势名称
→ 文献信号 → 工程问题 →
对本组实验/汇报的意义"展开，力求在实验事实与前沿方法之间建立清晰、可验证的对应关系。

前沿趋势总结：从"估得更准"到"更容易部署"

本总结承接前期对实验问题与 AI 方法对应关系的分析，不重复
MSCN、DeepDB、NeuroCard、PRICE
等模型的内部结构，重点讨论学习型基数估计在工程落地与前沿演进中仍面临的问题与趋势。所有实验数字来自
B/C/D 交付物，AI 方法部分为文献信号与工程问题分析，本组未训练或评测任何
AI 模型。

**趋势 1：从"单库准确率"走向"跨库可迁移"**

文献信号

PRICE（PVLDB
2024）在多个数据库上预训练，学习可迁移的分布与查询特征；ZeroCard（2025
预印本）进一步追求目标库"无原始数据、无查询日志、无重训练"。前期分析已将
PRICE 定位为"MSCN/DeepDB/NeuroCard → 可迁移 CE"演进中的重要节点。

工程问题

早期 learned CE
往往需要针对目标数据库重新准备训练查询、采集真实基数、训练模型。对于真实系统，这种准备成本直接影响方法能否落地。schema
差异与数据分布差异仍会影响迁移效果，但研究方向已从"单库
Q-error"扩展到"跨库准备成本与迁移能力"。

意义

S20 跨表相关 Q-error 仍为
100，说明跨表联合分布是原生统计的结构性盲区。跨库迁移正是为了降低这类场景在新数据库上的部署门槛。本报告应把
PRICE/ZeroCard
作为趋势重点，而非重复模型结构。这一趋势也把讨论从"哪个模型更准"自然过渡到"哪个模型更容易落地"。

**趋势 2：从"模型准确率"走向"系统级收益"**

文献信号

Bao 直接利用真实执行延迟作为反馈；前期分析已共同判断：Q-error 变小 ≠
计划一定切换 ≠ 查询一定变快。

工程问题

评价 learned CE 时，除了
Q-error，还需关注计划质量、端到端延迟、推理开销、更新成本。本组实验中，S16、S19、S20
的 Q-error 分别从
100→1、189.375→1、100→100，但三阶段物理计划均未切换；T09 的 10.322
倍误差出现在根节点，代价被 Hash Join 结构稀释，计划仍为 Hash
Join。这说明基数误差是否真正影响性能，取决于误差位置、误差大小和下游决策自由度。

意义

"误差危害 ≈ 误差大小 × 误差位置 ×
下游决策自由度"可作为解释评价边界的核心公式。评价链条应为：基数估计 →
Cost → 计划选择 →
执行时间，并附加泛化与部署成本。本组实验给出了干净的反例：Q-error
改善不自动等于性能改善，从而避免"用论文 Q-error
代替系统收益"的表述偏差。

**趋势 3：从"全替代"走向"协同共生"**

文献信号

DQ 代表端到端全替代路线，推理开销高、级联误差风险大；Bao 采用 Hint
干预，保留传统 CBO 安全兜底，在 JOB 上平均提升 2--3×
并大幅削减长尾延迟。

工程问题

全替代路线需要自底向上逐步生成计划，单条 SQL
推理可能达数百毫秒，难以满足 OLTP
低延迟要求；一旦底层某步决策偏差，误差会沿计划树级联放大。协同共生路线将
AI 作为顶层干预，传统优化器仍负责底层搜索与安全兜底，推理开销极低（Bao
通常 \<1 ms）。

意义

本组全部 20 条查询、144 份计划中，未观察到 Join 算法或 Join Order
切换。T11 虽然选择 Nested Loop，但候选代价差距大，计划稳健。这说明在
SF=1 轻量场景下，传统 CBO 仍具稳健性；AI
方法应聚焦传统统计失效的边界，而非全面替代。本组实验划出了传统 CBO
的能力边界，learned CE 应聚焦跨表相关（S20）、Join
后联合关系（T09）、统计输入偏差（T11）等边界场景。

**趋势 4：从"静态训练"走向"冷启动与在线适应"**

文献信号

专家轨迹行为克隆（Behavior
Cloning）、离线代价模拟器预训练、线上渐进微调（Progressive
Fine-tuning）是当前解决冷启动的主要策略。国产数据库 openGauss DBMind
与金仓 IQO 均采用"学习模式 + 自适应"路径。

工程问题

强化学习优化器若未经稳健初始化直接上线，随机探索可能产生灾难性执行计划，导致
CPU 独占、I/O 饱和、内存溢出。冷启动阶段必须引入策略防护网：先用传统 CBO
专家轨迹进行行为克隆，再在离线模拟环境中试错，最后以极低探索率上线微调。

意义

T11 的 n_distinct 采样偏差（l_orderkey 估计 383,583，真实约 150
万）说明静态统计会随数据变化失真。ALECE 这类动态 learned CE
将查询与当前数据状态共同编码，正是为了应对 workload drift
与数据更新。本组 T11
与国产数据库的工程实践串联起来，说明"数据会变、负载会变、模型需要持续适应"是
learned CE 必须面对的普遍问题。

**趋势 5：从"黑盒预测"走向"可解释与轻量化推理"**

文献信号

神经网络黑盒特性限制 DBA
对异常执行计划的诊断能力；模型压缩、知识蒸馏、端云协同成为降低推理开销的方向。

工程问题

高并发 OLTP
场景要求优化阶段延迟极低，复杂模型推理可能成为新瓶颈。同时，数据库管理员需要理解计划选择原因，缺乏解释性会影响
learned CE 在核心优化器中的部署信任。

意义

本组"误差危害 = 误差大小 × 位置 × 自由度"可作为解释性分析的切入点：即使
Q-error
很大，若误差在根节点或零自由度位置，也可能没有性能后果。这一规律可帮助
DBA 快速判断误差风险。同时，DQ 与 Bao
的推理开销对比说明轻量化不是可选项，而是 learned CE
进入核心优化器的前提。

**趋势 6：从"基数估计"走向"端到端学习优化"**

文献信号

Neo、Bao
等工作不再只学习基数，而是学习代价估计、计划选择甚至完整优化流程。Bao 用
Tree-CNN 提取计划上下文，再用 Bandit 选择 Hint 组合；DQ 则把 Join Order
选择建模为 MDP，端到端学习计划。

工程问题

基数估计只是优化链条的一环。如果只修正基数，但代价模型仍不准确，或计划搜索仍受启发式剪枝限制，优化收益可能被抵消。端到端学习优化试图把基数、代价、计划选择统一到一个学习框架中，但也带来推理开销、冷启动、可解释性等新问题。

意义

本组实验已经显示：T09 的 10.322 倍基数误差并未改变 Hash Join
计划，S16/S19/S20 的 Q-error
改善也未触发计划切换。这说明基数估计只是链条中的一环，真正决定性能的是"基数
→ Cost → 计划选择 →
执行时间"整条链路。端到端学习优化正是试图把这条链路纳入统一模型。本组实验可以作为"为什么需要端到端学习"的实证背景。

**趋势 7：从"单查询优化"走向"工作负载级优化"**

文献信号

金仓 IQO 面向整个工作负载推荐索引，而不是为单条 SQL 建索引；openGauss
DBMind 采集业务负载后统一调参。Bao 也在工作负载级别持续学习，而非逐条
SQL 独立决策。

工程问题

真实数据库面对的是工作负载，而不是孤立查询。索引推荐、物化视图选择、参数调优、查询重写都需要在工作负载层面权衡：为一条查询建索引可能拖慢写入，为一条
SQL 调参可能影响其他查询。单查询最优不等于工作负载最优。

意义

本组实验的 20
条查询是教学查询集，不代表真实工作负载；qerror_statistics.csv
按独立查询汇总，未做工作负载级加权。这一点可以作为"本组实验边界"的说明，也可作为未来方向：学习型方法不仅要降低单查询
Q-error，还要在工作负载层面平衡读写、延迟与资源。

**趋势 8：从"纯数据驱动"走向"知识与数据混合驱动"**

文献信号

ZeroCard 利用 schema
语义与预训练知识，减少对目标库数据与查询日志的依赖。传统 CBO
本身也大量使用约束信息（主键、外键、唯一约束、CHECK
约束）。近期工作开始把 schema
语义、业务规则、约束信息与数据驱动模型结合。

工程问题

纯数据驱动模型需要大量数据与标签，且难以解释；纯规则方法又难以覆盖复杂分布。混合驱动试图用先验知识约束模型、降低数据需求、提升可解释性与泛化能力。

意义

本组实验中的扩展统计（dependencies、MCV、ndistinct）本身就是一种"知识 +
数据"的混合机制：它既依赖数据采样，也依赖用户显式声明多列关系。S16/S19
被扩展统计修正，S20 仍失效，说明"知识 +
数据"的混合机制在跨表场景仍有边界。这与 ZeroCard
等方法的动机一致：如何在不访问目标库数据的情况下，利用 schema
语义完成估计。

**趋势 9：从"单机 PostgreSQL"走向"云原生与分布式"**

文献信号

PRICE 的多库预训练、ZeroCard 的零数据依赖、openGauss
与金仓的工程实践，都面向多数据库、多租户、云原生场景。分布式数据库还需要考虑数据分片、跨节点
Join、网络传输代价。

工程问题

云原生数据库面临动态资源供给、多租户隔离、跨库迁移、隐私合规等新问题。学习型基数估计需要在这些约束下工作：模型能否跨库迁移？能否在隐私受限时使用？能否适应分布式
Join 的代价结构？

意义

本组实验基于单机 PostgreSQL 17.6、Docker Linux
容器，未涉及分布式或云环境。这一点可作为实验边界说明，也可作为趋势延伸：S20
跨表相关的 Q-error 100
在单机场景已经出现，在分布式场景可能更严重，因为跨节点数据传输会放大基数误差的代价。PRICE
与 ZeroCard 代表的跨库、低依赖方向，正是为了应对这类场景。

**趋势 10：从"SQL 规则解析"走向"LLM 辅助语义理解"**

文献信号

近期出现利用 LLM 做查询重写、自然语言转
SQL、查询解释、甚至辅助基数估计的工作。LLM 可以理解 schema
语义、业务术语与查询意图，可能为基数估计提供额外上下文。

工程问题

LLM
推理开销大、延迟高、结果不稳定，难以直接嵌入优化器热路径。但可以在离线阶段辅助
schema
理解、查询重写、特征生成；或在线阶段以低频率调用，用于复杂查询的辅助判断。

意义

本组实验未涉及 LLM，但 T09 的业务语义（订单日期与发货日期的关系）恰好是
LLM
可能理解的"业务规则"，而传统统计无法表达。这可以作为未来方向的讨论点：LLM
能否帮助优化器理解这类业务语义，从而改善 Join
后相关性估计。但必须明确，本组未做任何 LLM 实验，仅作为趋势展望。

**趋势 11：从"固定代价模型"走向"硬件感知优化"**

文献信号

持久内存、GPU 加速、CXL
互联等新硬件进入数据库内核，传统代价模型的硬件假设已严重滞后。学习型优化器天然具备从真实执行中感知硬件特性的能力。

工程问题

传统 CBO 的代价公式中，随机 I/O 与顺序 I/O
的权重系数在数据库设计之初固化，难以自适应 NVMe
SSD、持久内存与云环境动态资源供给。学习型模型可以从真实执行反馈中学习硬件性能特征。

意义

本组 Cost 为优化器抽象单位，不能与毫秒直接相除。S16/S19 估计修正后 Total
Cost 保持 6122，S20 保持
5551.12，计划未切换，说明代价模型与真实性能之间仍有距离。未来 AI
优化可与硬件感知结合，而本组实验揭示的"代价模型与真实性能之间存在距离"这一问题，正是学习型方法可以发挥作用的空间。

总结

综合以上趋势，学习型基数估计正从"单库更准"走向"跨库可迁移、系统级收益与工程落地"。本组实验表明：传统
CBO 在单表、简单连接和同表相关场景仍具稳健性，S16/S19
可被扩展统计修正；真正困难的是跨表联合分布（S20）、Join
后相关性（T09）与统计输入偏差（T11）。这些边界问题正是学习型方法的研究动机，但
Q-error
改善不自动等于计划切换或查询加速，评价必须结合计划质量、端到端延迟、泛化能力与部署成本。本组未训练或评测任何
AI 模型，所有趋势讨论仅用于解释研究动机，而非宣称 AI 已优于
PostgreSQL。整组研究主线至此收束：从实验问题出发，划出传统机制边界，映射
AI
方法回应，再延伸到工程落地与前沿趋势，最终回到传统优化器与学习型方法协同关系的理性判断。
